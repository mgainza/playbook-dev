Arquitectura Frontend & React

Notas de trabajo sobre separación de responsabilidades, composición, manejo de estado y organización de código.

1. Separar la lógica de la presentación

Arquitectura

Un componente que maneja estado, efectos, validación y render a la vez solo se puede probar renderizándolo. Partirlo en dos capas rompe esa dependencia:

  • Custom hook (useAlgo): estado (useState), efectos, validación, formateo y llamadas a la API. Es la capa de dominio y se prueba como una función.
  • Componente de presentación: recibe props y devuelve JSX. No decide reglas de negocio ni dispara trabajo asíncrono.
// Lógica: testeable sin montar nada
function useSearch(query: string) {
  const [results, setResults] = useState<Result[]>([]);
  const [status, setStatus] = useState<Status>('idle');
  // ... efectos, cancelación, normalización
  return { results, status, isEmpty: status === 'ready' && !results.length };
}

// Vista: sin lógica que valga la pena testear
function SearchResults({ results, status, isEmpty }: Props) {
  if (status === 'loading') return <Spinner />;
  if (isEmpty) return <EmptyState />;
  return <List items={results} />;
}
Regla de oro: si para probar una regla de negocio necesitás renderizar UI, la regla está en el lugar equivocado.

2. Composición antes que configuración

Patrones UI

Cuando un componente acumula props booleanas (isCompact, hasIcon, showFooter), el problema no son las props: es que el componente está decidiendo cosas que deberían decidirse desde afuera.

  • Composición con children: el contenedor aporta caja, espaciado y estados de error; quien lo usa aporta el contenido.
  • Slots con nombre: si hay varias zonas, pasarlas como props de tipo ReactNode (header, actions) en lugar de multiplicar banderas.
  • Componentes compuestos: Tabs y Tabs.Panel comparten estado por contexto sin exponerlo al exterior.
// ✗ Cada caso nuevo agrega una prop
<Card title="Perfil" showAvatar hasFooter isCompact />

// ✓ El componente aporta la caja; el uso aporta el contenido
<Card>
  <Card.Header>Perfil</Card.Header>
  <Card.Body>{children}</Card.Body>
</Card>
Regla de oro: si soportar un caso de uso nuevo exige otra prop booleana, lo que falta es un punto de composición.

3. Clasificar el estado antes de elegir herramienta

Estado

La mayoría de las discusiones sobre "qué librería de estado usar" desaparecen al separar qué tipo de estado es cada cosa:

Tipo Ejemplo Dónde vive
Local de UI Menú abierto, foco, paso de un wizard useState en el componente
Derivado Total del carrito, lista filtrada Se calcula en el render
De servidor Respuesta de la API Capa de cache con revalidación
De URL Filtros, paginación, tab activo Query params
Global Sesión, tema, idioma Contexto o store
El estado derivado no se guarda: se calcula. Copiarlo con useEffect + setState agrega un render extra y una segunda fuente de verdad que tarde o temprano se desincroniza.

4. Datos remotos: modelar los cinco estados

Datos

Toda lectura remota tiene cinco estados posibles, y el que casi siempre falta es el cuarto:

  1. Inicial, antes de pedir nada.
  2. Cargando.
  3. Error, con opción de reintentar.
  4. Vacío: la petición salió bien y no hay resultados. No es lo mismo que cargando.
  5. Con datos.

Si el fetch se hace a mano, hay que ignorar las respuestas obsoletas: sin eso, una búsqueda rápida puede pintar el resultado de una consulta anterior.

useEffect(() => {
  let cancelled = false;
  const controller = new AbortController();

  fetchResults(query, { signal: controller.signal })
    .then(data => { if (!cancelled) setResults(data); });

  return () => { cancelled = true; controller.abort(); };
}, [query]);
Una capa de cache (React Query, SWR, o los loaders del framework) ya resuelve cancelación, deduplicación y revalidación. Escribir esto a mano se justifica solo en casos puntuales.

5. Organizar por feature, no por tipo de archivo

Estructura

Agrupar por tipo (components/, hooks/, utils/) obliga a tocar cinco carpetas para cambiar una sola funcionalidad. Agrupar por feature mantiene junto lo que cambia junto:

src/
├── features/
│   └── checkout/
│       ├── components/   --> UI propia de la feature
│       ├── hooks/        --> lógica y estado
│       ├── api/          --> acceso a datos
│       └── index.ts      --> única superficie pública
├── components/           --> UI genérica, sin reglas de negocio
└── lib/                  --> utilidades sin dependencias de UI
  • Una feature se comunica con otra solo a través de su index.ts.
  • Lo que sube a components/ es lo que ya se usa en dos features, no lo que "quizás" se reutilice.
  • Si borrar una feature deja código huérfano en otra carpeta, el límite estaba mal puesto.

6. «Element type is invalid»: importaciones rotas

Debugging

El error "Element type is invalid: expected a string or a class/function but got: undefined" casi siempre significa que el componente llegó como undefined. Tres causas, en orden de frecuencia:

  • Default vs. named: el módulo exporta export const Button y se importa como import Button from (o al revés).
  • Dependencia circular: dos módulos se importan entre sí a través de un index.ts de re-exportación. Uno de los dos se evalúa a medias y sus exports quedan vacíos.
  • Módulo ausente en ese entorno: el import se resuelve a undefined en el build (paquete solo de servidor, condición de exports distinta, alias mal configurado).
Solución: dentro de una misma feature, importar por ruta directa (./Button) en lugar de pasar por el barrel. Los barrels son para consumo externo, no para uso interno.
